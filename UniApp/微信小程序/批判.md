---

**a：打开和响应的速度普遍比网页慢多了**

确实。小程序的启动流程比纯网页复杂得多：需要先启动微信客户端内的 JSBridge 环境，加载基础库，解析 `app.json` 配置，再逐层初始化页面栈。相比之下，浏览器打开一个网页就是解析 HTML → 请求资源 → 渲染，链路短得多。

---

**b：那是它愚蠢的分包机制造成的**

这个吐槽精准命中要害。小程序的**分包加载策略**确实很迷：

- 主包有 **2MB** 的硬性上限（整个小程序所有包加起来不能超过 **20MB**）
- 页面跳转时如果目标页面在分包中，需要**先下载整个分包**才能跳转
- 不像 Web 的 Code Splitting 那样可以做到组件/路由级别的按需加载，小程序的分包是粗粒度的物理文件切割

结果就是：要么主包臃肿塞满常用页面，要么分包切换时卡成 PPT。Webpack/Vite 的按需加载粒度可以到模块级别，小程序这相当于回到了手工拆文件的时代。

---

**a：开发体验也差 / b：热重载慢**

微信开发者工具的"热重载"（他们叫"热更新"）确实一言难尽。原理上它不像 Vite 那种基于 ESM 的 HMR（Hot Module Replacement），而是：
- 文件改动后需要重新编译整个小程序包
- 通过 websocket 推送到模拟器/真机
- 模拟器里重新加载基础库、重新执行 `App()` 和 `Page()` 的生命周期

这个流程下来，稍微大一点的项目等 3-5 秒是常态。对比 Vite 利用浏览器原生 ESM 实现的毫秒级 HMR，确实像是从石器时代穿越来的。

---

**a：本身是个套皮浏览器，却缺少大量web端本身具有的功能**

这个"套皮浏览器"的说法不完全准确，但情绪到位了。小程序运行环境基于 WebView（iOS WKWebView / Android X5 内核），但上面盖了一层厚厚的**微信运行时**：

被砍掉/限制的 Web 能力包括但不限于：
- 无法直接操作 DOM（没有 `document` 对象）
- 受限的 CSS（不支持部分高级选择器、`position: fixed` 有坑、自定义字体限制多）
- 没有完整的 BOM（`window` 对象被替换为 `wx` / `tt` / `my` 等各家自己的命名空间）
- 网络请求必须用 `wx.request`，受域名白名单、并发数、HTTPS 强制限制
- 无法使用标准 Web Storage，只能用微信封装的 `wx.setStorage`
- 没有 Service Worker、Push API、WebRTC 等现代 Web API

**b 说的"怕商户跑了"**确实是一部分原因——如果小程序能直接跳转到外部网页、能随意发 push 通知、能自由操作 DOM 做一套自己的 UI 框架，那开发者完全可以把小程序当做一个"启动器"，核心逻辑全放在 H5 里，绕过微信的支付抽成、数据监控和审核机制。

但另一部分原因是**安全与管控**的借口。微信需要在 iOS 上规避 Apple 的 IAP 抽成争议，需要确保所有内容和交易都在其可视范围内，所以主动选择了一个**阉割版的 Web 子集**。

---

**a：开发者工具大量bug拖着不解决，或者难以复现 / b：对chromium内核缺乏基本的敬畏**

这是开发者工具（IDE）层面的问题。微信开发者工具基于 Electron + Chromium 内核，但微信团队对它做了大量魔改：

- 内置了一个**修改版 Chromium** 来模拟小程序运行环境
- 加入了自定义的 DevTools 扩展、模拟器、调试协议转换层

问题就出在这些魔改上：
- Chromium 版本通常**严重滞后**于主流版本（你用的 Chrome 都到 130+ 了，开发者工具里可能还在跑一个 fork 自 90+ 的版本）
- 微信自己维护的 DevTools 前端和 Chromium 后端之间的**协议兼容性**经常出问题
- 真机调试和模拟器的行为**不一致**（模拟器里好好的，真机上就崩了，或者反过来）

"b"说的"缺乏敬畏"很形象——Chromium 是一个极其复杂的工程，Google 数千工程师维护，版本迭代极快。微信团队想在上面叠一层自己的运行时，却缺乏足够的人力去跟上上游的更新节奏，结果就是：
- 各种奇怪的渲染 bug（文字截断、动画卡顿、层叠上下文异常）
- 调试器断点失灵、控制台输出丢失、性能面板数据不准
- 内存泄漏（开发者工具本身就是个吃内存大户）
