## 2026-06-01

### 第3题 [高级] — async/await 与事件循环

**题目：**
```js
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}
async function async2() {
  console.log('async2');
}
console.log('script start');
async1();
console.log('script end');
```

**错误答案：**
```
script start → async1 start → async1 end → script end → async2
```

**正确答案：**
```
script start → async1 start → async2 → script end → async1 end
```

**解析：**

1. `async1()` 被调用，进入 `async1` 函数体
2. `console.log('async1 start')` — 同步执行，立即输出
3. `await async2()` — **关键点**：`await` 右边的表达式（`async2()`）会先**同步执行**，所以 `async2` 里的 `console.log('async2')` 立即输出
4. `await` 将 `async1` 中剩余的代码（`console.log('async1 end')`）**挂起为微任务**，放入微任务队列
5. 当前调用栈继续执行同步代码 → `console.log('script end')`
6. 同步代码全部执行完毕，清空微任务队列 → `async1 end`

**核心规则：**
> `await` 后面的代码不是立即执行，而是被"切片"放入微任务队列。同步代码优先，微任务次之，宏任务最后。

**关联知识点：**
- Event Loop 执行顺序：同步 → 微任务（Promise.then, queueMicrotask, await 后续）→ 宏任务（setTimeout, I/O）
- async/await 本质上是 Promise 的语法糖，会被编译为 `yield` + Generator 或 Promise 链
- `await` 右侧表达式同步求值，左侧后续代码异步执行

## 2026-06-04

### 第2题 [中级] — var + setTimeout 循环终止值（js-001）

**状态：答错 ❌**

**题目：**
```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
```

**错误答案：**
```
2 2 2
```

**正确答案：**
```
3 3 3
```

**解析：**

循环条件是 `i < 3`，所以 i 的取值过程是：
- 第1次：i = 0，满足条件，进入循环体，setTimeout 注册回调
- 第2次：i = 1，满足条件，进入循环体，setTimeout 注册回调
- 第3次：i = 2，满足条件，进入循环体，setTimeout 注册回调
- 第4次：i = 3，**不满足条件，循环终止**

循环结束后 `i === 3`。三个 setTimeout 回调共享同一个 `i`（var 是函数作用域），执行时看到的都是这个 3。

**常见陷阱：** 下意识把最后一个有效索引 2 当成循环终止值，但循环终止条件是 `i < 3`，当 i 递增到 3 时才退出。

**修复方案：**
```js
// 方案1：用 let（块级作用域）
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// 输出：0 1 2

// 方案2：用 IIFE 创建私有作用域
for (var i = 0; i < 3; i++) {
  (function(j) {
    setTimeout(() => console.log(j), 100);
  })(i);
}
// 输出：0 1 2
```

**关联知识点：** 见核心知识点.md — 五、闭包与作用域

### 第3题 [高级] — V8 隐藏类与 Inline Caching（js-012）

**状态：部分正确**

**用户答案：**
- 隐藏类：结构一样的对象共享一个类，动态增删属性会导致原类失效，性能下降，应提前定义好属性。
- Inline Caching：不清楚。

**补充解析 — Inline Caching：**

> Inline Caching（内联缓存）是 V8 在属性访问上做的一个热点优化。当你反复读取某个对象的属性（如 `obj.x`），V8 会缓存 "该对象的隐藏类 + 属性名 → 偏移量" 的映射。下次访问时，先检查隐藏类是否匹配，如果匹配就直接按偏移量取属性值，跳过字典查找。

**为什么动态增删属性会破坏 IC？**
- 动态添加属性会改变对象的隐藏类
- 隐藏类变了，之前缓存的 "类 → 偏移量" 映射就失效了
- V8 被迫回退到慢路径（字典查找），性能下降

**优化代码示例：**
```js
// 差：运行时动态添加属性
const p = { x: 1 };
p.y = 2;   // 隐藏类变化，IC 失效
p.z = 3;   // 再次变化

// 好：构造函数中预先声明所有属性
function Point(x, y, z) {
  this.x = x;
  this.y = y;
  this.z = z;  // 初始化时统一创建
}
const p = new Point(1, 2, 3);
p.y = 4;  // 隐藏类不变，IC 继续命中
```

**关联知识点：** 见核心知识点.md — 六、V8 性能优化

### 第2题 [中级] — Event Loop 是什么？（js-005）

**状态：部分正确（执行顺序答对，定义需补充）**

**用户答案：** 顺序是同步 → 微任务 → 宏任务。Event Loop 的准确定义不清楚。

**完整解析：**

**Event Loop 的定义：**
> Event Loop 是 JavaScript 运行时（浏览器或 Node.js）用来协调**同步代码执行**与**异步任务调度**的一种机制。它是一个无限循环，不断从各种任务队列中取出任务并执行。

**为什么需要 Event Loop？**
JavaScript 是单线程语言，同一时间只能做一件事。但现实中需要处理网络请求、定时器、用户交互等异步操作。Event Loop 就是 JS 处理异步任务的调度器。

**执行顺序（核心规则）：**
```
1. 执行当前调用栈中的所有同步代码（清空调用栈）
2. 执行所有微任务（microtask）队列中的任务，直到清空
3. 执行一个宏任务（macrotask）队列中的任务
4. 重复步骤 2-3
```

**常见分类：**

| 类型 | 包含 |
|------|------|
| **同步** | 普通函数调用、console.log、赋值运算等 |
| **微任务** | Promise.then/catch/finally、queueMicrotask、MutationObserver、async/await 的后续代码 |
| **宏任务** | setTimeout/setInterval、I/O 操作、UI 渲染、setImmediate（Node.js） |

**关键细节：**
- 微任务优先级高于宏任务。每执行完一个宏任务后，必须先清空全部微任务，才能执行下一个宏任务。
- 如果微任务里又产生了新的微任务，会继续执行，直到微任务队列彻底清空。

### 第3题 [高级] — 通用 curry 函数（js-011）

**状态：未理解实现原理**

**用户困惑：** "一个函数的返回值怎么能同时是函数和 number 呢？"

**核心解答：**

curry 函数的实现依赖 **JavaScript 的隐式类型转换** —— 当函数被用在需要数值的上下文时，会触发 `valueOf()` 或 `toString()`。

**实现代码：**
```js
function curry(fn) {
  return function curried(...args) {
    // 如果传入的参数够了，直接执行原函数
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }
    // 参数不够，返回一个新函数，继续收集参数
    return function(...nextArgs) {
      return curried.apply(this, args.concat(nextArgs));
    };
  };
}

// 使用
const add = curry((a, b, c) => a + b + c);
console.log(add(1)(2)(3)); // 6
console.log(add(1, 2, 3)); // 6
console.log(add(1, 2)(3)); // 6
```

**进阶版（支持 `add(1)(2)(3)` 和 `add(1,2,3)` 且自动求值）：**

如果用户希望 `add(1)(2)(3)` 这种形式**直接得到 6 而不是函数**，需要利用 `valueOf` / `toString`：

```js
function add(...args) {
  const sum = args.reduce((a, b) => a + b, 0);
  
  function fn(...nextArgs) {
    return add(sum, ...nextArgs);
  }
  
  // 当函数被当数字用时，自动返回 sum
  fn.valueOf = () => sum;
  fn.toString = () => sum;
  
  return fn;
}

console.log(+add(1)(2)(3)); // 6
console.log(add(1, 2, 3));  // 6（如果直接 console.log，会显示 [Function]）
```

**关键原理：**
- `+add(1)(2)` 这里 `+` 运算符需要数字，JS 会尝试调用 `valueOf()`
- `console.log(add(1)(2) == 3)` 比较时也会触发转换
- 这就是函数能"表现"得像数字的原因 —— 不是真的变成了 number，而是 JS 在类型转换时走了后门

**关联知识点：**
- 函数是一等公民，可以作为返回值
- 闭包：内部函数记住外部函数的参数
- `valueOf` / `toString`：对象/函数在需要原始值时的自动转换机制

### 第2题 [中级] — new 运算符做了什么（js-009）

**状态：答对但死记硬背 ⚠️**

**用户答案：**
> 新建一个对象，设置其 prototype 为构造函数的 prototype，绑定 this。

**遗漏点：**
- 漏了**执行构造函数代码**（第4步）
- 漏了**处理返回值**（第5步：显式返回对象则返回该对象，否则返回新对象）
- 不理解"为什么要链接到构造函数的 prototype"和"绑定 this 具体指什么"

**深入理解 — 为什么要链接到构造函数的 prototype？**

这不是一个随意的规定，而是 **面向对象继承体系的核心设计**。构造函数是"工厂"，prototype 是"共享方法仓库"。

```js
function Person(name) {
  this.name = name;  // 实例独有的属性
}

// 方法放在 prototype 上，所有实例共享，节省内存
Person.prototype.sayHi = function() {
  console.log('Hi, I am ' + this.name);
};

const p1 = new Person('Alice');
const p2 = new Person('Bob');
console.log(p1.sayHi === p2.sayHi); // true
```

链接 prototype 的目的：
- 让实例 **共享** 构造函数 prototype 上的方法（内存优化）
- 实现 **原型链继承**：实例找不到的属性会沿 `__proto__` → `prototype` → `Object.prototype` 向上查找

**"绑定 this" 具体指什么？**

```js
function Person(name) {
  // 这里 this === 新创建的空对象 {}
  this.name = name;  // 给这个新对象添加属性
  this.age = 20;
}
```

- 构造函数内部的 `this` 不是全局对象，而是 **步骤1创建的新对象**
- 相当于构造函数被 `call/apply` 了，`this` 被硬编码指向新实例
- 构造函数通过 `this.xxx = ...` 给新对象"填充"属性

**完整流程（5步）：**
```
1. 创建新对象 {}
2. 链接原型: obj.__proto__ = Constructor.prototype
3. 绑定 this: 构造函数内的 this 指向这个新对象
4. 执行构造函数代码
5. 处理返回值: 构造函数显式返回对象则返回该对象，否则返回新对象
```

**关联知识点：** 见核心知识点.md — 七、new 运算符

### 第3题 [高级] — LRU 缓存 O(1) 实现（js-018）

**状态：未掌握 ❌**

**用户反应：** "这个东西怎么可能 O(1) 呢？"

**核心解答：**

直觉上缓存淘汰需要"排序"，排序至少是 O(log n)。但答案是 **HashMap + 双向链表**。

| 数据结构 | 职责 | 为什么 O(1) |
|---------|------|-------------|
| **HashMap** | 存储 key → 节点的映射 | `Map.get/set/delete` 是 O(1) |
| **双向链表** | 维护"使用顺序" | 节点自带 prev/next 指针，删除/插入只需改指针，无需遍历 |

**关键操作：**
- `get(key)`：Map 查找到节点 → 链表删除该节点 → 链表插入头部 → 返回 value。全部 O(1)。
- `put(key, value)`：Map 查重/更新 → 链表插入头部 → 如果超容量，删除链表尾部 → Map 删除对应 key。全部 O(1)。

**为什么双向链表能做到 O(1) 删除？**

因为每个节点知道自己前后是谁（`prev` 和 `next` 指针）。删除一个节点只需要：
```js
node.prev.next = node.next;
node.next.prev = node.prev;
```
不需要遍历链表找位置。数组的 `splice` 做不到这一点，因为数组元素不知道自己前后是谁。

**完整实现代码：** 见核心知识点.md — 八、LRU 缓存

**记忆策略：**
> **HashMap 管"找"，链表管"排"**。Map 让你瞬间找到数据，链表让你瞬间调整顺序。单用任何一个都做不到 O(1)，组合起来就是面试标准答案。

**关联知识点：** 见核心知识点.md — 八、LRU 缓存
